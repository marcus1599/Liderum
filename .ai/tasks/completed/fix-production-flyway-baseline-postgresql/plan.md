## Estado do incidente

- **Produção:** indisponível no Render após iniciar Flyway em PostgreSQL 18.4.
- **Release Verdict:** BLOQUEADO.
- **Task pausada:** `tasks/paused/extend-tenant-integration-coverage-to-events-and-attendance/`; seu planejamento foi preservado sem descarte.
- **Causa raiz:** CONFIRMADA. V1, linha 1, tenta criar `guilds` em schema legado sem histórico Flyway; PostgreSQL retorna SQLState `42P07` / `relation "guilds" already exists`.

## Diagnóstico inicial confirmado

1. O banco Render contém schema legado sem histórico Flyway. O primeiro `CREATE TABLE guilds` da V1 falha com `42P07`; não é falha de Hibernate, JWT ou beans posteriores.
2. Dados legados são descartáveis. A estratégia é banco novo/vazio; baseline, reconciliação, `IF NOT EXISTS`, repair e edição manual de history foram descartados.
3. `V1__baseline_schema.sql` cria as tabelas `guilds`, `member`, `users`, `team`, `event` e `attendance`; adiciona FKs depois de criar todas as tabelas e então cria índices. A ordem de FKs é compatível com as referências declaradas.
2. A V1 usa `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP`, `VARCHAR`, FKs, unique constraints e índices. Essas construções passaram no H2, mas H2 não prova compatibilidade PostgreSQL.
3. Os mappings JPA esperam os mesmos nomes de tabela/coluna relevantes e Hibernate está configurado com `ddl-auto=validate`; os erros de `EntityManagerFactory` e beans de segurança posteriores são coerentes com um schema que não foi criado, não uma causa independente demonstrada.
4. A aplicação usa Flyway 9.22.3 via Spring Boot 3.2.0. As release notes dessa versão são de outubro de 2023 e indicam suporte de PostgreSQL somente até 15; o aviso do runtime é consistente com isso. A documentação atual da Redgate suporta PostgreSQL 18, mas isso descreve versões atuais, não valida retrospectivamente 9.22.3.
5. Classificação do warning: **C — possível fator, mas não causa comprovada.** O Flyway chegou a validar e iniciar a V1; sem SQLState/statement não é possível atribuir a falha ao suporte de versão.
6. Docker CLI existe, mas o daemon Docker Desktop Linux não está disponível nesta máquina. Não há `psql` nem alternativa de runtime PostgreSQL local detectada. A reprodução PostgreSQL vazio ainda não foi realizada.

## Primeira rodada: ações permitidas

1. Iniciar Docker Desktop ou disponibilizar PostgreSQL descartável autorizado para validar V1 contra PostgreSQL 18, em banco efêmero com profile/configuração prod equivalente.
2. Confirmar as seis tabelas, PKs, FKs, uniques, índices, identities, tipos, nullability, `flyway_schema_history`, Hibernate validate e startup.
3. Se V1 falhar em banco vazio, parar e investigar o erro real; não editar SQL por tentativa.
4. Se V1 passar, preparar reprovisionamento Render e smoke test; aguardar autorização operacional explícita antes de destruir/substituir banco.

1. PostgreSQL descartável vazio: Flyway aplica V1 e registra `flyway_schema_history` versão 1.
2. Contexto Spring sobe com `ddl-auto=validate` e PostgreSQL real.
3. Testes direcionados de Flyway/PostgreSQL e `./mvnw.cmd clean verify`, aguardando resultados finais verificáveis.
4. Regressão de onboarding, RBAC, multi-tenancy e rate limit comprovada pela suíte.
5. QA revisa a reprodução, isolamento do banco descartável e regressões; Security revisa secrets/dados de migration e integridade tenant; SRE revisa configuração Render/Compose, operação e recuperação; Auditor decide Task/Release Verdict.
